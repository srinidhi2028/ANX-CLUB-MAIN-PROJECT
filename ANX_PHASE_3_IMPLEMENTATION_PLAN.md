## 2. Proposed canonical data contract — approval required

This is a recommendation for review, not an approved schema.

**Payments:** retain a single payment record keyed by Razorpay order ID, for example `payments/{orderId}`. Proposed fields: `schemaVersion`, `provider`, `orderId`, `paymentId` (nullable until known), `ownerUid` (verified Firebase UID), `purpose` (`membership` or `event`), `planId` or `eventId`, integer `amountMinor` in paise, ISO `currency`, approved payment `status`, `createdAt`, `updatedAt`, `verifiedAt`, `paidAt`, and an idempotency/fulfillment key. Price, purpose and owner are server-derived. Client-submitted identity and amount are not authoritative.

**Memberships:** retain one history record per paid grant/renewal in `memberships/{membershipId}`. Proposed fields: `schemaVersion`, `membershipId`, `ownerUid`, `planId`, `billingPeriod`, membership `status`, integer `amountMinor`, `currency`, Firestore Timestamp `startsAt`/`expiresAt`, `paymentOrderId`/`paymentId`, and `createdAt`/`updatedAt`. Link a membership grant to one payment order and make that relationship unique for fulfillment. Define the stable membership ID or uniqueness mechanism before implementation. Maintain any `users/{uid}` premium fields as a clearly defined projection, not a second source of payment history.

**Events and compatibility:** event registrations should reference the verified payment order/record; the approved event-registration write remains with the Events owner. Read both legacy shapes during a staged transition: V1 order-keyed `pending`/`paid` records, legacy payment-ID-keyed `success` records, random-ID membership records, and current user-profile fields. Do not infer that a legacy `success` or client-supplied amount proves a captured payment. Do not delete, re-key, or backfill existing records without a separately approved migration, backup, dry run, reconciliation and rollback plan.

## 4. Business decisions blocking membership and payment behavior

| Decision | Options and consequences | Recommendation for review — not adopted |
|---|---|---|
| **A. Month-end expiry** | Clamp Jan 31 monthly start to February's last day; preserve JavaScript calendar rollover (currently reaches Mar 3 in the observed IST example); or use an approved fixed-duration policy. These produce different entitlement lengths. | Use calendar-month billing with end-of-month clamping (Jan 31 → Feb 28/29), explicitly tested. Requires business approval. |
| **B. Timezone** | IST calendar computation/display matches the likely local billing day; UTC calendar boundaries can shift displayed dates for users in India. | Store instants as UTC Firestore Timestamps, calculate the approved billing-calendar boundary explicitly in `Asia/Kolkata`, and display in IST. Approve timezone and boundary semantics. |
| **C. Activation threshold** | Razorpay authorization means payment method was approved; capture is the later captured payment state. Activating before capture can grant access to an uncaptured payment. | Require provider-confirmed `captured` before paid fulfillment. Razorpay’s integration guidance says to verify signature and check captured status before delivering; it describes fetching status/API or webhooks for status checks. [Razorpay integration steps](https://razorpay.com/docs/payments/server-integration/python/integration-steps/) and [Razorpay security checklist](https://razorpay.com/security/checklist/). |
| **D. Early renewal** | Start at today's successful payment date (can shorten already-paid time) or extend from an unexpired membership's expiry (preserves purchased duration). Expired-member behavior also needs definition. | Extend from the current expiry only when still active; otherwise start from confirmed capture time. Requires business approval. |
| **E. Payment captured, membership write fails** | Synchronous transaction where supported; or durable pending-fulfillment/retry/reconciliation workflow. Student needs a state that distinguishes captured payment from still-processing entitlement. | Persist verified payment first with a recoverable fulfillment state, fulfill idempotently with retry/reconciliation, do not ask the student to pay again, and show “payment received; membership activation processing” until confirmed. Requires agreement on durable workflow and customer support handling. |

Also confirm exact prices/plan IDs, event price ownership, admin complimentary grants, status vocabulary, refund/dispute/chargeback policy, late and out-of-order events, payment-history retention, and historical legacy-record trust rules.

## 5. Testing environment and acceptance plan

**Available now (inspection only):** existing Jest and mocks; payment auth, ownership and signature tests. The Phase 2 reports record 5 suites/23 tests passed and a focused 2-suite/10-test pass (overlapping tests, not additive). No new tests have been run for Phase 3 because implementation is not approved.

**Firebase Emulator:** no `firebase.json` or `.firebaserc`; Firebase CLI is not installed in the project; emulator host variables are not configured; local ports 8080 (Firestore) and 9099 (Auth) had no listener. Emulator tests are therefore **BLOCKED** until an approved local emulator setup is provided. Do not point tests at production/shared Firebase.

**Razorpay test mode:** local environment inspection found a public key ID with a test-mode prefix and a configured API secret; values were masked. Their pair validity was not checked. No webhook secret is configured. The key ID prefix alone does not prove the credentials authenticate or that requests reach test mode. Confirm the test credential pair with its owner before any approved test-mode request. No live Razorpay call or payment was made. Razorpay documents the order fetch response fields (`id`, integer amount in currency subunits, currency and status) in its [Orders API reference](https://razorpay.com/docs/api/orders/fetch-with-id/).

**Test gates after an approved task:** add/run deterministic unit/mocked tests first; add emulator tests when an emulator is available; use Razorpay test mode only after credential-pair confirmation and explicit task approval. Cover the project’s required cases: auth missing/invalid/expired/valid/cross-user; order creation, price/paise, invalid values, signature/order/payment/currency mismatch, uncaptured/failed/cancelled and repeats; membership activation/duplicate/renewal/expiry/month-end/ownership/dashboard/partial failure; the three event classes; refunds/disputes/chargebacks and webhook duplicate/retry/out-of-order/reconciliation if approved. Run relevant Jest suites, TypeScript (`npx tsc --noEmit`), lint (`npm run lint`) and production build (`npm run build`) as appropriate to each task. Record exact outputs; do not call mocks integration tests.

**Git:** read-only `git status --short` was attempted at both `ANX-CLUB-main` and its parent; both returned “not a git repository.” The project folder is a reparse-point directory and has no visible `.git` entry. Existing/uncommitted teammate changes therefore cannot be confirmed by Git status. No branch, commit, push, merge, or history change was made. Establish the team's actual checkout/Git workflow before implementation.
