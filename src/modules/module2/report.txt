--------------------------------------------------------------------------------
1. OBJECTIVE
--------------------------------------------------------------------------------
The primary objective of Module 2 is to design, implement, and deploy a resilient 
Backend-for-Frontend (BFF) Aggregator API layer for the A.N.X V1 Member Dashboard. 

Key targets:
- Consolidate seven distinct sub-services into a single unified JSON payload.
- Establish an asynchronous parallel execution pipeline that minimizes latency.
- Achieve high-fault-isolation so that individual backend/micro-service failures 
  do not compromise the entire user interface dashboard.
- Support dual-mode operations: standard Cloud Firestore storage in production 
  and clean local simulated mock data during local development and testing.
- Track real-time endpoint latency and performance telemetry for diagnostics.

--------------------------------------------------------------------------------
2. SYSTEM TECHNOLOGY STACK CONFIGURATION
--------------------------------------------------------------------------------
Module 2 is built on the following technologies and library configurations:

- Core Framework: Next.js v14.2.35 (configured with App Router & dynamic API routes)
- Programming Runtime: Node.js with TypeScript v5
- Database & Admin SDK: Firebase Admin SDK v13.10.0 (Firestore Collection integration)
- Client/UI State: React v18 & React DOM v18
- Utilities and Telemetry: 
  * Performance API (native performance.now() instrumentation)
  * Framework Dynamic Config Mode: 'force-dynamic'

3. MODULE 2 TIER ARCHITECTURE AND ACCESS MATRIX
--------------------------------------------------------------------------------
The module is built with a strictly decoupled 3-tier architecture:

                          +-------------------------+
                          | Presentation/BFF Route  | (app/api/v1/module2/)
                          +-------------------------+
                                       |
                                       v
                          +-------------------------+
                          | Service Orchestration   | (services/)
                          +-------------------------+
                                       |
                                       v
                          +-------------------------+
                          |   Data & Mock Layer     | (data/)
                          +-------------------------+

- Presentation/BFF Route: 
  Interprets incoming HTTP headers and query strings, executes parallel services, 
  and compiles the final payload.
- Service Orchestration Layer:
  Contains domain logic (users, memberships, projects, events, bookings, 
  announcements) with conditional switches for Mock vs Database retrieval.
- Data & Mock Layer:
  Defines seed data schemas and helper query functions for local offline testing.

ACCESS CONTROL & ROLE-BASED RECOMMENDATION MATRIX:
Downstream services dynamically customize return payloads depending on User Role 
and Membership Tier permissions:

MEMBERSHIP ENRICHMENT LOGIC:
A user's active membership record is enriched with state parameters:
- tier = 'Premium' | 'Enterprise' AND status = 'active' => isPremium = true.
- status = 'expired'   => isPremium = false, upgradeCTA = "Subscription expired..."
- status = 'pending'   => isPremium = false, upgradeCTA = "Payment pending..."
- tier   = 'Basic'     => isPremium = false, upgradeCTA = "Upgrade to Premium..."

4. CORE FEATURE ENGINEERING AND FUNCTIONAL IMPLEMENTATION
--------------------------------------------------------------------------------
Module 2 engineers several core design patterns:

- Parallel Execution Aggregator:
  Fires seven promises concurrently. Rather than using Promise.all (which fails 
  on the first rejection), Module 2 implements Promise.allSettled to isolate 
  faults. If a downstream service fails, it yields an empty object or array 
  but lets the remaining services deliver their content.

- Telemetry & Performance Instrumentation:
  Uses a custom instrument() wrapper that tracks the start and end execution 
  time of each sub-service down to the millisecond. This metadata is returned 
  in the client payload under the 'meta.trace' field, facilitating profiling 
  and system health checks.

- Email-to-UID Resolution Middleware:
  Accepts either a unique user identifier (UID) or a standard email address. 
  An identity resolver query matches email patterns to internal IDs prior 
  to execution.

- Automated Error Recovery & Fallbacks:
  Failed service checks fall back safely to corresponding empty data types:
  * User Profile service failure      => {}
  * Membership service failure        => {}
  * Projects service failure          => []
  * Event / Booking service failure   => []
  * Announcements service failure     => []

--------------------------------------------------------------------------------
5. QA TESTING PROTOCOL & QUALITY ACCEPTANCE CRITERIA
--------------------------------------------------------------------------------
Testing covers endpoint reliability, validation rules, and schema verification.

TEST PROTOCOL & METHODOLOGY:
- Mock Verification:
  Verify that adding query param "?mock=true" bypasses remote Firestore 
  connectivity and resolves instantly against internal mock files.

- Resilience Testing via Fault Injection:
  BFF dashboard GET endpoint accepts "?fail=" query parameter. Testers supply 
  comma-separated service names (e.g., "?fail=user,projects") to verify that:
  1. The API route returns HTTP Status Code 200 (Success).
  2. The failed services are labeled "rejected" in the meta.trace array.
  3. The response JSON structure remains valid, with empty placeholders in the 
     failed fields.

- Authentication & Security Boundary Check:
  Production database mode checks for an 'x-user-id' request header. Queries 
  lacking this header must fail with an HTTP 401 Unauthorized status code.

QUALITY ACCEPTANCE CRITERIA:
- Schema Integrity: Every successful response MUST match the TS DashboardResponse interface.
- Latency Overhead: The aggregator must process all parallel calls within 15ms 
  above the slowest single downstream service.
- Error Tolerance: A failure in a non-critical component (e.g. announcements or 
  projects) must never cause a complete dashboard load failure for the client.
